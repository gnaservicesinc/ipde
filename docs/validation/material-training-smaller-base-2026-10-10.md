# Smaller material-training base

Assessment dated October 10, 2026. **A smaller network is the stronger direction than running additional PBRnxt trainers on this Mac. Start with a shallow native convolutional material student, preserving 512 × 512 source pixels and existing map encodings.** This is a proposed new model family, not a replacement applied to the current app. No weights were downloaded, models trained, or builds started for this assessment.

## What is consuming the time

The retained [512 measurement evidence](native-training-throughput-2026-10-10.json) records a changed-input rank-8 map-decoder step at **5.706484 s**. In the two-material production fixture, input preparation took about **9 ms** and the CPU optimizer **26–34 ms** per step; warmed steps took **4.93–5.76 s**. Turning off frequent validation saves validation work but does not remove the forward/backward compute within those steps. The short GPU observations averaged 86.6–89.4% system-device utilization; a second trainer would compete for much of the same resource. See the separate [concurrency assessment](training-concurrency-2026-10-10.md).

The [native model](../../src/TextureStudio/Services/NativeMaterialModel.swift) retains a width-96 hybrid convolution/transformer generator, two encoder blocks per level, two decoder blocks per level, four fusion blocks and 12 RRDBs in the selected final branch. Even height-only training computes **all four generator decoder branches**, their fusion and all generator map tails before the selected RRDB branch. Other generator branches are learned inputs to height; pruning them is not an equivalent implementation of the pretrained base. A changed-input 512 step submitted 212 stages. Lower LoRA rank reduces adapter work without eliminating this backbone.

The [earlier trial record](../material-pbrnxt-trial-results.json) counts **86,763,756 parameters** in the complete base. It also records rejected material quality in prior fitting experiments. That count includes the complete loaded network, not a measured operation count for one selected target. Current native execution omits the original final 4× enlargement, but retains its substantial generator/refinement network. The authors' original network is designed for diffuse-to-PBR generation and includes a 12-block refinement network per output. [PBRnxt source](https://github.com/aaf6aa/PBRnxt/blob/main/pbrnxt_net.py), [author description](https://github.com/aaf6aa/PBRnxt).

These observations support reducing network work. They do not establish a specific speedup, including a 1,000× gain, from any candidate. No smaller candidate has been timed or visually accepted on this Mac.

## Three realistic options

| Option | Output fit and weights | Native implementation and training | Decision |
| --- | --- | --- | --- |
| Shallow convolutional material student, based on a small U-Net/NAF-style backbone | New height, roughness and normal heads fit the existing outputs. NAFNet authors provide restoration checkpoints and training code, but those checkpoints are not albedo-to-PBR weights. | Convolution, depthwise convolution, normalization, multiplication, pooling and spatial upsampling can be expressed in MPSGraph. A new small material model must learn from paired material targets; restoration transfer is an optional initialization experiment. | **First candidate.** One shared encoder/decoder, small task heads, much less architectural work, and no dependency on four generator branches. |
| Reduced PBRnxt student | Retains a familiar task formulation. No smaller pretrained PBRnxt checkpoint was verified in this review. | Proposed width 32/48, one block per encoder/decoder level and 2–4 RRDBs instead of 12. New tensor shapes require scratch training or distillation. Keeping attention still carries substantial graph/compilation complexity. | Secondary candidate if the simple student loses necessary relief detail. This is an architecture change, not a LoRA setting. |
| DeepBump / MobileNetV2 U-Net | Author-supplied `deepbump256.onnx` predicts normals; height is computed from normals. No roughness prediction and no released training code. | Shipped inference uses CPU ONNX Runtime and overlapping 256 tiles. An Apple GPU port would need graph/weight conversion; native retraining needs a separately implemented architecture and recipe. | Useful compact normal/height comparison, **not a complete trainable replacement**. |

NAFNet's official code separates configurable width and block depth, and the repository offers width-32 restoration weights. Its network is meant to restore RGB: the RGB residual connection and final RGB head must be replaced for material outputs. A reduced-depth variant cannot directly load the full published checkpoint. The native port must also preserve normalization and pooling semantics, without importing automatic external padding into the app's input contract. [Official architecture](https://github.com/megvii-research/NAFNet/blob/main/basicsr/models/archs/NAFNet_arch.py), [released models and configs](https://github.com/megvii-research/NAFNet).

NAFNet's license file identifies its code as MIT, with separate BasicSR notices. PBRnxt's repository is MIT; its shipped third-party notices still need preservation. DeepBump's repository is GPL-3.0 and explicitly says its training code is unavailable; that makes direct incorporation a different licensing and engineering choice. This review identifies repository licenses, not a legal conclusion about every weight artifact. [NAFNet license](https://github.com/megvii-research/NAFNet/blob/main/LICENSE), [PBRnxt license](https://github.com/aaf6aa/PBRnxt/blob/main/LICENSE), [DeepBump repository](https://github.com/HugoTini/DeepBump).

The DeepBump author identifies its backbone as a MobileNetV2 U-Net. Its current color-to-normal code averages RGB to grayscale and processes 256-pixel tiles. Height integration uses a Fourier method and then stretches each image to its own minimum and maximum; importing that unchanged would violate this app's raw-height contract. It also lacks global structure on larger images according to the author. [Backbone description](https://hugotini.github.io/deepbump.html), [inference source](https://github.com/HugoTini/DeepBump/blob/master/module_color_to_normals.py), [height source](https://github.com/HugoTini/DeepBump/blob/master/module_normals_to_height.py), [height limitations](https://hugotini.github.io/normalheight).

## Concrete first prototype

Use three downsampling levels, channels `32 → 64 → 128 → 256`, one NAF-style block per level, one bottleneck block, and a symmetric shared decoder. Use a three-channel input and three independent linear output heads: one height channel, one roughness channel and three normal channels. Begin training only the height head with the shared backbone; add the other targets with explicit per-head losses and missing-target masks after the first result is useful. Train the small backbone directly instead of freezing most of a random new model and fitting LoRA alone.

A source-level parameter calculation for this proposal is **1,129,893 parameters** at width 32, or **288,981** at width 16. These numbers are analytical counts, not instantiated models or performance measurements. They assume three encoder/decoder levels, one block at each, one bottleneck, 3×3 input/output convolutions and five total output channels, with the upstream NAF block's default expansion of two. They are roughly 77× and 300× fewer weights than the recorded complete PBRnxt base; parameter ratios are not speed ratios.

For reproducibility, a NAF block at channel count `c` has `7c² + 33c` parameters under those assumptions. The input plus five output channels contribute `73w + 5`; each down convolution contributes `8c² + 2c`, and its corresponding up convolution `8c²`. Sum two blocks at each `c ∈ {w, 2w, 4w}`, one block at `8w`, and these input/down/up counts. There are seven blocks in total. This is a proposed shallow task network, not the authors' published restoration configuration.

Keep input/target grids at their declared native size, the existing diffuse transfer, original UInt16 height codes converted to Float32, and declared normal conventions. Export raw numeric predictions without per-image stretching. Internal downsampling is part of the network; it must not change the saved training grid or replace targets with smaller images. Give every checkpoint a new architecture identifier and base hash. Existing PBRnxt LoRAs depend on its exact layer names/shapes/base and **cannot transfer directly**. Preserve their existing backend and choose the new family explicitly.

For fitting, use the existing paired maps as the primary supervision. Optional teacher distillation can add shape/detail guidance from PBRnxt only where its predictions have been visually useful; copying its rejected relief and artifacts should not be the objective. Restoration weights may initialize matching encoder tensors, but do not confer pretrained PBR capability. Scratch training trades per-step efficiency for the need to learn material priors; total time-to-useful-result remains unknown.

The next work should be one short prototype decision: a handful of warmed 512 steps to establish actual wall time and memory, followed by a small controlled fit and visual relief comparison against source and current base. Do not start another hours-long full-dataset run or a broad optimization campaign before that decision. If the width-32 student is still slow, reduce full-resolution depth/width or try width 16; if fast but structurally wrong, improve supervision or capacity. Only then investigate physical batching across multiple materials. The smaller backbone reduces work per material; concurrent full PBRnxt copies do not.

The research used read-only Hugging Face model discovery and primary author repositories/pages. A limited `PBRnxt` Hub search returned no matches; this is not proof that no third-party smaller weights exist. No pretrained complete compact replacement satisfying all current contracts was verified.
